# 内容编导前台文本格式合同

本文件是内容编导链路阶段性交付文本的唯一格式真源。业务判断留在各子 Skill；标题、字段名、字段顺序、缺省写法和展开条件只在这里定义。持久化《赛道与内容数据库》的四部分赛道认知库与后台加工库信息架构由 [赛道数据库统一模板](../jiangdao-content/references/track-database-template.md) 管理；单篇详情仍使用本合同的十步格式。其他文件只能引用对应真源，不得复制、改名或另起模板。

## 一、公共规则

1. 先判断当前回复属于**正式交付物**还是**普通交流**。完整拆解、候选清单、生产决策卡、逐字稿等正式交付物使用本合同模板；解释概念、回答疑问、指出问题、确认状态和简短进度使用自然语言，不套模板。
2. 一次回复只展示当前最有用的一个主结果。进度、后台池、运行记录和方法解释不与正式交付物并列。
3. 正式交付物在聊天、Markdown 文件和数据库详情页中使用相同标题和主栏目顺序。详情页可以在对应栏目内部保留完整证据；聊天只展示影响理解和决策的信息。
4. 正式交付物的固定字段没有证据时写 `不可得（原因）`、`待核实（原因）` 或 `不适用`。逐篇拆解中一组来源字段全部缺失时，可以合并成一句缺口说明，避免连续展示空字段。
5. 条件字段只有在合同明确写明触发条件时才能出现；用户明确要求深挖时，在固定字段内部增加内容，不增加新的平行栏目。
6. 后台可以保存完整证据、传播链、框架、机制卡、替代解释、运行状态、校验代码和身份归属审计；这些字段默认不进入前台。
7. 前台先说用户现在需要理解或决定的内容，再补必要依据。相同意思只说一次，不把一句判断拆成“当前判断、判断依据、规则说明、处理结论”四段重复表达。
8. 把内部状态翻译成自然中文。只有错误会阻止用户继续、用户正在排查系统，或用户明确索要时，才显示 `TRACK_POOL_SCOPE_INSUFFICIENT`、`PRODUCTION_INPUT_OK` 等内部代码。
9. 禁用前台术语：`原作肉身`、`肉身保留`、`AI压缩版`、`双发动端`。需要表达相同含义时使用本合同规定的自然说法。
10. 赛道数据库前台不显示问题 ID、出现次数、样本数、证据状态、身份归属审计、候选状态、淘汰理由或运行说明。具体选题和短期内容机会只在当次选题共创中展示。
11. 数量可以由用户明确覆盖；正式交付物的字段、分组顺序和单条结构不能随数量变化。

## 二、公共首尾

文件型交付物第一行固定为：

```text
# <交付物名称>
```

聊天中的完整交付物可省略一级标题，但主结果内部的栏目名必须与本合同一致。普通交流不需要一级标题、固定栏目或缺省字段。

只有用户需要确认、补充材料、执行现实动作，或当前结果需要明确交接去向时，才在回复底部使用：

```text
【下一步】
去向：<一个明确去向>
现在只做：<一个清晰动作>
带回：<一种确认、素材或真实结果；没有则省略>
```

普通解释、判断、状态回复和已经完整回答的问题不强行追加《下一步》。需要动作时只保留一个去向和一个动作；没有现实动作时自然收尾。

## 三、赛道关键词确认区

```text
# 赛道关键词确认区

核心赛道词：
本轮任务词：
相邻可用词：
排除词：
本轮验证问题：
```

已有当前版本确认记录时，只显示：

```text
本轮复用的核心赛道词：<词1>、<词2>、<词3>
```

## 四、内容种子候选清单

```text
# 内容种子候选清单

## 1｜<一句具体的内容种子>

种子原点：<本人经历、判断、变化或原话>
市场连接：<对应的赛道问题或爆款证据>
当前成熟度：可形成选题 / 需补本人材料 / 需补赛道证据
还需要你补充什么：无 / <例如：赛道方法论、相关经历或真实结果>
推荐理由：<为什么现在值得继续>
来源：<本人记录与赛道证据的直达入口>
```

最多展示 3 条，每条重复同一结构。用户选中一条后，按“匹配现有赛道证据 → 形成具体选题 → 确认选题 →《生产决策卡》”继续；调取阶段不生成逐字稿。

## 六、逐字稿

```text
# 角色标注逐字稿

来源：
转写状态：成功 / 部分成功 / 失败 / 待人工复核
角色状态：单人 / 已标注 / 待复核
待核实词：无 / <词与位置>

## 完整逐字稿

<按原顺序呈现正文；多人内容固定使用“角色：内容”>
```

时间轴、缓存、引擎和运行元数据留在后台；用户明确要求时才在正文之后追加附件链接。

## 七、逐篇爆款拆解

单条与批量使用同一条“先还原 → 再理解 → 再拆选题 → 再判断传播 → 最后沉淀资产”的推理链。批量时完整结束一篇再进入下一篇。

```text
# 逐篇爆款拆解

## 1｜<原始标题>

内容概览：<用一段自然语言还原作者从什么问题讲起、怎样推进、给出什么答案、最后落到哪里；用户跳过逐字稿仍能独立理解整篇内容>
内容推进：<用 3—6 个节点表示原作实际讲述顺序>

### 01 来源与数据

来源：<平台>｜<作者>｜<发布时间>
原标题：
原链接：
可见数据：<只显示当前已取得的关键数据与采集时间>
证据状态：<全文、评论、视觉及会影响判断的关键缺口；技术运行数据留在后台>

### 02 推送语与推送标签

原作包装：<推送语、推荐文案、话题标签、搜索词和平台标签中实际取得的内容；全部不可得时合并说明>
证据状态：<原平台可见 / 采集记录 / 不可得；不由 AI 补写>

### 03 完整逐字稿

完整逐字稿/正文：<详情页内嵌完整文本；单条聊天可完整展示，批量聊天至少提供可直接打开的完整文本入口>
关键视觉信息：不适用 / <仅写已经核验且会影响理解的信息>

### 04 赛道问题

赛道问题：<比当前原选题高一个抽象层级、能在赛道内长出多个不同选题的核心问题；原作已处于赛道层时不强行上提>
问题证据：<正文、评论、访谈、咨询、搜索或其他直接来源；只有正文或抽象范围超出单条证据时标候选，并说明本文验证的具体场景>

### 05 选题怎么来的

加工动作：未明显加工 / 元素迁移 / 选题具体化 / 收益显化 / 损失显化，可多选
具体变化：<作者在赛道问题上增加或收窄了什么>
判断依据：<标题、推送语、正文或视觉中的直接证据>

### 06 原选题

原选题：<作者最终选择讨论的对象、场景和问题，保持答案开放>

### 07 作者答案

一句话答案：<作者对原选题给出的核心回答>
作者怎样讲清楚：<按原作顺序，用一段连贯叙述还原论证、案例、步骤和结论；不能只列抽象要点>
关键方法或判断：<确有必要时提炼，避免重复上一段>
适用边界：<作者明说或证据能够支持的边界>

### 08 为什么能传播

传播判断：<自由判断最关键的传播因素，不套固定标签>
判断依据：<标题、推送语、正文、视觉、作者身份、平台数据等证据>
证据边界：<评论验证放到下一节；缺点击、留存、完播或对照数据时不写确定因果>

### 09 评论区洞察

评论验证：<用户主要接住什么，以及它如何支持或修正传播判断>
代表原话：<只展示 1—3 条会改变判断的真实表达>
继续长出的问题：<最多 2 个真正值得继续研究的问题；没有则写无>
证据边界：<评论不可得时写明原因，不用作者正文或 AI 推断补齐>

### 10 最值得拿走

主要带走：<只保留这条内容最值得复用的一项能力或判断>
具体借法：<说明借哪一层、怎样借，不能只写资产名称>
暂不借：<最容易误抄、证据不足或依赖原作者的部分>
下一步用途：进入选题共创 / 只存研究 / 补证后再判断
```

固定约束：

- 01—10 是唯一前台顺序；详情页和聊天中的字段名、顺序保持一致。
- “内容概览”是逐篇拆解的阅读入口，必须覆盖起点、推进、答案和落点。它不能只写一句抽象内核，也不能要求用户读取逐字稿后才能理解。
- `赛道问题 → 选题怎么来的 → 原选题 → 作者答案` 必须分开，不能把答案、标题包装或 AI 推断写进赛道问题。
- 原选题必须能解释为赛道问题在某个人群、阶段或场景中的一种具体发生方式。赛道问题只能长回当前原题时通常过窄；宽泛到无法判断目标用户矛盾时则过宽。
- “选题怎么来的”只识别原作者实际使用的加工动作；无法从证据确认时写“未明显加工”或“待核实”。
- “为什么能传播”允许自由判断，但必须同时给出依据和证据边界；评论只在“评论区洞察”中承担验证、修正和继续挖题功能。
- 详情页必须内嵌完整逐字稿、正文或逐页 OCR；批量聊天为控制长度可以给直达全文入口，但数据库详情页不能只给路径。
- 内容框架、实际推进链、可借条件、形式处理、替代解释和详细资产关联继续保存在后台，用于形成第 08 与第 10 节。
- 数据缺口、赛道认知库映射、后台选题加工、完整候选资产和技术验收留在后台。前台第 10 节只帮助用户回答“这条主要学什么、接下来怎么用”。

## 八、选题候选清单

尚未取得当前项目、IP、赛道和目标人群范围内的用户校准时，先进行普通对话式共创。每轮只测试一条规则，给出两条候选，请用户选择一条、认可两条或全部 Pass，并记录原因；这一阶段不套正式清单模板。

校准完成后的完整选题共创默认生成 10 条，前台统一为一份连续编号的候选清单。所有候选都从当前赛道问题池中的完整问题句加工而来，不按类型分组或规定配比。用户明确指定总数时，只覆盖当前任务；后续仍恢复默认 10 条。

```text
# 选题候选清单

<仅单篇题源共创显示：题源范围：单篇题源共创｜围绕这一篇拆出的赛道问题继续加工，不代表赛道已经验证。>

## 1｜<一句自然、直接的完整选题；开放问题或待认领的方向性命题>
题源原话：<逐字显示赛道问题池中的完整问题句>
生成关系：<说明保留了什么核心需求，使用了哪些加工动作，具体改变了什么；禁止只写“来自数据库”>
建议：<一段自然建议>
来源：<赛道问题及其后台来源索引的直达入口>

## 2｜<一句自然、直接的完整选题；开放问题或待认领的方向性命题>

<重复相同单条结构，连续编号至 10>
```

固定约束：

- 题源原话必须直接显示，用户无需点开文件才能判断来源。
- 来源必须直达对应赛道问题及其后台来源索引；找不到问题来源关系时，该候选作废。
- 选题可以是答案开放的问题，也可以是等待用户认领的方向性命题。后者仍是候选，建议只提供候选角度，不冒充用户已确认观点。
- 选题必须从当前赛道问题继续生长，不能照抄来源原选题，也不能只替换数字或近义词。生成关系需要说明采用的加工动作以及与题源问题的实质差异。
- 元素迁移、选题具体化和损益显化只加工已经进入问题池的问题；新增身份、经历、成绩、因果和效果不得凭空添加，内容无法交付的题面承诺作废。
- 每条候选都要让目标客户感知具体损益，并能撑起一条完整内容。只能充当一个信号或分论点的小现象留在素材层，不进入正式候选。
- 具体条件需要兼顾代入和共鸣覆盖率。少数人才会遇到的特殊剧情不因“真实存在”自动进入候选。
- 最想点击的人应当是当前目标客户。主要吸引非目标人群批评目标客户的题目需要淘汰或重做。
- 后台保留每条候选的赛道问题句、加工动作和来源关系，前台不显示分组标题。
- 后台同时保存《选题候选审计》，用于核验校准状态、核心需求、加工依据、观点状态、目标受众、损益、内容承载力、共鸣范围、身份归属与候选差异；审计字段不进入本清单前台。
- 赛道问题池共创不显示题源范围提示；单篇题源共创只显示上述一行，不展开证据审计。

## 十一、剪辑审核页与成片交付

- 逐字稿删减与编排审核页只使用 `course-cut-review` 的当前格式，内容编导和剪辑 Skill 不再生成第二套审核页。
- 成片交付固定显示：`当前版本`、`成片/工程`、`同版本字幕`、`同版本逐字稿`、`验收结果`、`已知限制`。

## 十二、发布候选

每个平台固定使用 A、B、C 三组；每组字段顺序为：

```text
A｜操盘手推荐
标题：
推送语：
标签：
为什么推荐：
```

B、C 使用完全相同结构。用户明确只需要一种时可以减少组数，字段不能减少或改名。

## 十四、格式优先级与变更

1. 用户在当前任务明确指定格式时，仅覆盖本次输出，并在首行写 `本轮格式覆盖：<内容>`。
2. 用户只改变数量、平台或内容范围，不视为格式变更。
3. 任何长期格式修改只改本合同；各 Skill 和参考文件继续引用，不复制新模板。
4. 旧任务恢复时按本合同重新装配前台，不沿用旧标题和旧字段顺序；后台历史文件保留原样，避免破坏证据链。
