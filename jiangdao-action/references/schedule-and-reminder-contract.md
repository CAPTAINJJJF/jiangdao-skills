# 飞书日历与 Codex 提醒调度合约

## 分工

| 节点类型 | 默认调度 |
|---|---|
| 需要本人连续投入时间完成的工作 | 飞书日历事件 |
| 到点检查、回收数据、确认状态或唤醒操盘判断 | Codex 提醒 |
| 同一里程碑既要执行时间又要后续回收 | 两者组合，但时间和目的必须不同 |
| 自动发布、客户联系、报价、成交或替用户决策 | 禁止自动执行，只能提醒 |

不要为同一时间、同一目的同时创建两条通知。日历事件可以使用飞书自带的开始前提醒；Codex 提醒应承担独立的数据回收、经营判断或续接任务。

## 生成待创建清单

从已确认计划提取未来节点，输出：

```text
节点 ID / 来源任务 / 调度类型 / 标题 / 开始时间 / 结束时间或提醒时点 / 时区 / 目的 / 写入状态
```

- 默认时区使用 `Asia/Shanghai`；计划另有明确时区时按计划。
- 标题只写任务，不把时间、地点和人物重复写入标题。
- 飞书日程描述包含来源计划版本、任务 ID、交付物、证据指标和回来反馈材料。
- Codex 提醒包含到点需要检查什么、读取哪些项目文件、带回什么结果；不包含自动发布或对外发送指令。
- 已过去节点不创建；历史计划只保留记录。

## 飞书日历写入

1. 完整读取 `lark-calendar` 及预约日程工作流；默认使用 `--as user` 和用户主日历。
2. 判断是新建还是更新。已有 `event_id` 或能唯一匹配同一节点时更新；不确定时先列候选，禁止重复创建。
3. 时间明确时检查当前日程与忙闲；出现冲突时给出可用时间方案并等待选择。
4. 时间模糊时使用飞书日历的时间推荐流程，不自行猜一个具体时点直接写入。
5. 写入前展示待创建或待更新清单；用户确认后执行。
6. 创建成功后使用命令返回的 `event_id` 作为结果，不为确认而重复查询；返回信息不足或用户要求复查时才查询。
7. 分别记录成功、失败和待授权状态。飞书失败不影响已经成功的 Codex 提醒，反之亦然。

## Codex 提醒

1. 优先用于计划已定义的下一次动作、数据回收和阶段判断节点。
2. 创建前检查现有自动化；同一节点已有提醒时更新，不创建重复项。
3. 一次性节点使用一次性提醒；重复的数据回收或经营判断才使用重复规则。
4. 用户只说“提醒我”但未确认计划时，先确认具体节点；不把整份草案转成自动化。
5. 创建后保存自动化名称、触发时点、时区、ID 和状态。

## 计划变化与同步

- 只同步未来节点；已完成任务、历史日程、已触发提醒和原截止日期保持可追溯。
- 日期变化时更新对应未来飞书事件和 Codex 提醒，不新建副本。
- 任务取消时先展示将取消的未来日程和提醒，获得确认后再处理。
- 用户可以只授权本轮、单个节点或某一种调度；未授权部分保持“建议设置待确认”。

## 完成标准

- 每个节点只使用必要的调度层，没有双重骚扰。
- 飞书日历与 Codex 提醒分别有真实状态和 ID，不用一层成功冒充整体成功。
- 所有时间可追溯到已确认计划，并使用明确时区。
- 没有越过内容确认、发布、客户联系、报价和成交闸门。
