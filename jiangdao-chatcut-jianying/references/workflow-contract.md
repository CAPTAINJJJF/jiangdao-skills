# ChatCut 转剪映执行合约

## 1. 状态机

```text
待确认处理方式
→ 待准备代理
→ ChatCut 初剪中
→ 初剪/正式包装已确认待读取
→ 时间线双读回待确认
→ 剪映与能力预检
→ 转换清单已锁定
→ 剪映草稿待构建
→ 素材已导入
→ 轨道已生成
→ 字幕已落轨
→ 工程已保存待读回
→ 剪映实际播放待验收
→ 可交外部精修
```

进入本合约前，上游《剪辑工作流确认卡》必须已有用户确认时间。课程、演示、口播、访谈和混合型视频沿用各自已确认的内容与画面逻辑，交接阶段不重新猜测。任何失败都保留原片、代理、ChatCut 项目、转换清单和已生成草稿。不得在旧草稿上反复覆盖试错。每次恢复先读取任务目录唯一 `EDITING_STATE.json` 并运行 `../jiangdao-edit/scripts/validate_editing_state.py`；TASK、manifest、聊天和界面标签只提供证据。

## 2. 上传前确认卡

用户尚未说明时，只问会改变处理结果的一组短问题：

1. 保持原顺序只删重复句、讲到一半重说和明显口误，还是允许调整结构？
2. 使用原倍速还是 1.1 倍速？当前项目默认候选为 1.1。
3. 是否有必须保留的长停顿、动作或表情？
4. 本次交付只要主视频轨，还是还要字幕轨、动画轨？
5. 唯一正式项目/时间线、当前阶段、交付范围和验收口径分别是什么？

用户已经明确回答的项不得再次询问。用户只说“把素材放进去”且没有处理规则时，停在上传前确认。

## 3. 整条处理前预检

预检在任何整条导出、渲染或草稿构建之前完成，并写入状态卡：

- 剪映专业版安装路径、版本和目标草稿目录；
- ChatCut 当前账号/会员能力；
- Motion Graphics、透明背景或 alpha 导出能力；
- 所有目标输出绝对路径及可写性；
- `handoff.mode=direct_multitrack|clean_base_overlay_srt`；
- 正式时长、画幅、帧率、预期轨道数、字幕数量/首尾和额外素材数。

先用 1—3 分钟代表片段验证新参数和受限能力。首次出现会员或透明动效限制后保存证据，立即切换用户已授权的降级模式；相同能力、相同参数不再用整条视频重试。未获降级授权时停在预检。

## 4. 代理合同

- 原片只读，代理单独存放；代理不得成为最终剪映素材引用。
- 保持画面方向、比例、完整声音和稳定帧率。竖屏 1728×3072 原片可使用约 540×960 的 H.264/AAC 代理作为起点。
- 代理与原片必须能由 manifest 明确映射；同名单素材优先保持相同文件名。
- 上传完成后记录 ChatCut asset、项目 ID、时间线 ID、代理绝对路径和原片绝对路径。

## 5. ChatCut 时间线双读回合同

只读取用户确认完成的正式时间线。正式导出前连续完成两次读回：

1. MCP/Agent 当前工作时间线：项目 ID、时间线 ID、名称、时长、画幅、帧率和轨道摘要；
2. ChatCut 桌面当前可见并被选中的时间线：记录同一组字段。

两次结果必须与状态卡中的正式时间线完全一致。桌面选择可能决定实际导出对象，MCP 工作时间线一致仍不足以放行。分页读取正式时间线直到没有剩余项，至少记录：

- 项目 ID、时间线 ID、画布宽高、帧率；
- 当前 ChatCut 操作端（桌面版或网页）、MCP 时间线、桌面可见时间线与时间线版本；
- 每个视频片段的稳定序号；
- `timeline_start_frame`、`duration_frames`；
- `source_start_frame`；
- `playback_rate`，缺省按 1；
- 对应工作代理和最终本地原片；
- 字幕卡的 `start_frame`、`end_frame`、文本和当前 revision（需要字幕轨时）。

按目标起点排序后检查：无负值、无重叠、首段从 0 开始、相邻差值不超过允许的舍入误差、最后结束帧等于时间线总结束帧。动作停顿应位于保留片段内部，不能被“闭合主轨间隙”误删。

隐藏、静音、禁用或关闭可见性的 ChatCut 轨道仍然存在。它们不能作为“剪映不会带入”的证据，也不能进入交付白名单。

## 6. 两种固定交付模式

### `direct_multitrack`

仅在预检确认当前 ChatCut 与剪映链路可稳定保留交付轨、透明/混合信息和时间基准时使用。转换 manifest 只列出状态卡白名单中的轨道；测试轨、审核提示、隐藏恢复轨、完整原素材和废弃版本一律排除。先跑代表片段，轨道数、透明效果或字幕落轨任一失败时停止整条构建并切换已授权降级模式。

### `clean_base_overlay_srt`

这是固定降级方案：

1. 新建干净 ChatCut 项目 A，只放交付底轨，排除段落动效、字幕、提示、测试轨和隐藏轨，导出 `base_video`；
2. 新建干净 ChatCut 项目 B，只放交付动效覆盖内容，时间线从 00:00:00 开始，与底轨同画幅、帧率和总时长，导出 `motion_overlay`；
3. 从同一最终时间基准生成独立 `subtitles_srt`；
4. 在新剪映草稿把底轨放在 00 点，覆盖轨放在 00 点并按确认的混合模式设置，再导入 SRT；
5. 底轨、覆盖轨、SRT 之外的媒体和轨道预期为 0。

干净项目通过轨道白名单重新构建。复制正式项目后隐藏非交付轨道不满足此要求。若透明导出受限，可使用用户确认的黑底覆盖轨与剪映混合模式；混合模式需在剪映实际播放验收。

## 7. Manifest

`scripts/build_jianying_spec.py` 接受 JSON：

```json
{
  "name": "ChatCut_初剪_剪映版",
  "width": 1080,
  "height": 1920,
  "fps": 30,
  "ratio": "9:16",
  "working_media_path": "/absolute/path/to/proxy.mp4",
  "working_width": 540,
  "working_height": 960,
  "output_speed": 1.1,
  "clips": [
    {
      "timeline_start_frame": 0,
      "duration_frames": 86,
      "source_start_frame": 2751,
      "playback_rate": 1
    }
  ],
  "captions": [
    {"start_frame": 0, "end_frame": 84, "text": "字幕示例"}
  ],
  "caption_style": {
    "fontSize": 15,
    "color": "#FFFFFF",
    "x": 0,
    "y": 0.65
  }
}
```

未提供字幕时只生成主视频轨。`output_speed` 缺省为 1.1；用户明确原倍速时写 1.0。manifest 和生成的 compile spec 都作为任务记录保存。多轨 manifest 必须显式写出轨道白名单、每轨片段数、00 点、总结束点和素材路径，不能从 ChatCut 的可见状态推断。

多轨时使用顶层 `video_tracks`，每项包含 `name`、绝对 `working_media_path`、`working_width`、`working_height`、`allow_timeline_gaps` 和自己的 `clips`；此字段存在时取代单轨的顶层 `working_media_path` 与 `clips`。底轨和全长覆盖轨都从 `timeline_start_frame=0` 开始，结束帧必须一致。

## 8. 构建顺序

1. 读回并校验状态卡；完成时间线双读回和能力预检。
2. 定位当前可用的 `capcut-cli` 与 Node；记录工具版本。没有已安装工具时，使用可信来源获取固定版本并校验完整性，不把临时下载路径写成 Skill 常量。
3. 只为 `direct_multitrack` 或代理构建运行 `build_jianying_spec.py manifest.json spec.json`，随后执行 `compile --check`。
4. `clean_base_overlay_srt` 先核验两个干净 ChatCut 项目的轨道白名单，再各导出一次整条底轨与覆盖轨；正式文件验证通过后不因剪映装配问题重复渲染。
5. 关闭剪映后生成独立新草稿。导入完成只更新 `assets_imported`，轨道真正出现后才更新 `tracks_created`。
6. 执行 lint；只对确认属于微秒舍入的主轨间隙使用 `--fix`。需要 relink 时核对所有引用。
7. 导入 SRT 后读取文本轨及片段数量，确认首条和末条时间码，再更新 `captions_on_timeline`。
8. 保存草稿并重新读取 `draft_content.json`，运行 `info`、`lint` 和 `validate_jianying_draft.py`，按状态卡传入预期轨道数、每轨片段数、媒体路径、字幕数/首尾、总时长和未引用素材数；全长底轨/覆盖轨同时启用 `--require-video-start-zero --require-video-equal-end`。
9. 在剪映中实际播放规定检查点，通过后更新 `playback_checked`。

实际命令参数以当前 `capcut-cli --help` 为准。工具或剪映版本变化时先验证命令面，不复制旧版本参数猜测执行。

## 9. 版本与命名

- 30 秒兼容性样例：`<项目>_兼容测试_<日期>_30s`。
- 正式独立草稿：`<项目>_初剪完整版_<日期>`。
- 三轨或倍速扩展：`<项目>_三轨_1.1x_<日期>`。
- 新版本必须新建目录。用户确认可以覆盖前也优先保留可回退副本。

## 10. 每次剪映修改后的复验

导入 SRT、设置/改变混合模式、增加/删除/移动轨道、重新链接素材或保存新版本后，都要重新核对：

- 总时长与正式时间线一致；
- 视频、音频、文本轨数量与状态卡一致；
- 片头、至少一个中段点和片尾实际播放；
- 字幕首条、末条、总数及越界情况；
- 底轨与覆盖轨都从 00 点开始，需要全长覆盖时结束点一致；
- 额外素材、未引用素材、测试轨和隐藏恢复轨为 0。

剪映首页可见、素材库中出现文件、导入工具返回成功、草稿 JSON 存在都只证明各自步骤，不能合并写成“工程完成”。

## 11. 自动化与人工确认

可自动化：安装路径与版本读取、输出路径检查、MCP 时间线读取、分页清单、轨道白名单、代理/底轨/覆盖轨导出、SRT 生成、草稿构建、轨道与素材计数、00 点/总时长/字幕首尾/未引用素材校验。

必须人工或桌面视觉确认：桌面当前可见时间线、ChatCut 会员提示和实际可用导出选项、剪映混合模式的视觉结果、字幕可读性、片头/中段/片尾的真实播放、音画同步。人工确认结果也要写回状态卡或验收记录。

## 12. 验收记录

至少保存：

- ChatCut 项目与时间线 ID；
- ChatCut 操作端、MCP/桌面双读回及初剪/包装确认版本；
- 剪映安装、ChatCut 会员、透明动效能力和目标路径预检；
- 交付模式及轨道白名单；
- 原片、代理、manifest、compile spec 和剪映草稿绝对路径；
- ChatCut 片段数、剪映片段数、总时长、速度分布；
- material 条目数、唯一素材路径、缺失数；
- lint 错误、警告、信息提示；
- 剪映版本及开头、中后段、片尾播放结果；
- `assets_imported`、`tracks_created`、`captions_on_timeline`、`draft_saved`、`playback_checked` 的独立证据；
- 每次剪映修改后的总时长、轨道数、片头/中段/片尾、字幕首尾和额外素材复验；
- 字幕轨和动画轨是否实际生成、是否验收。

只有“剪映实际打开并播放”完成后，才能向用户说转换成功。
