# 赛道数据库统一模板

本文件是内容编导新建、迁移、更新和导出赛道数据库的唯一结构真源。所有 IP、学员、内测案例和多赛道母库使用同一信息架构；项目身份、数据边界和证据来源必须隔离。

赛道数据库是一份长期积累的“赛道认知库”。它帮助用户看懂一个行业正在讨论什么、用户怎样描述问题、什么表达方式反复有效。具体选题和短期内容机会在选题共创阶段生成，不进入长期数据库。

## 前台结构

汇总入口页面的默认标题固定为：

> # 赛道数据库

版本号、“赛道认知版”等维护说明留在后台，不写进前台标题。

`赛道与内容数据库.md` 的标题下先显示一行：

> 核心赛道词：<词1>、<词2>、<词3>

这里只写当前 IP 已确认的 1—3 个长期核心赛道词，不计入下面四部分，也不把工作接触赛道自动写成核心赛道词。本轮任务词、相邻可用词、排除词、确认状态、版本和更新时间留在后台。

`赛道与内容数据库.md` 固定展示四部分：

1. **赛道理解**；
2. **赛道问题池**；
3. **用户语言与评论问题库**；
4. **赛道传播规律**。

多赛道入口按“一个赛道一整段”展示：完整看完一个赛道，再进入下一个赛道。

当用户同时经营自己的赛道，又因工作长期接触其他行业时，总入口分成两层：

1. **自己持续经营的赛道**：可进入当前 IP 的内容研究，但仍需经过当次选题共创；
2. **工作中接触的赛道**：用于理解客户、评估业务和快速进入陌生行业，不自动进入当前 IP 的选题池。

同一条样本可以被多个赛道视角读取；原始记录、详情页和证据只保留一份，各赛道库保留关联。

前台不展示高价值选题池和当前内容机会。选题共创只读取赛道问题池中的完整问题句，先完成当前项目与目标人群的口味校准，再按独立的选题加工规则生成当次候选。后台选题加工库只保存历史样本实际使用过的加工动作，作为研究资产，不直接参与候选生成。

问题 ID、样本数、证据状态、身份审计、候选状态、失败原因、运行日志和完整来源关系全部留在后台。

## 推荐目录

```text
赛道与内容数据库.md
赛道数据库/
├── <赛道名>/
│   ├── 赛道数据库.md
│   └── 赛道汇总库.json
├── 后台关联索引.json
└── 赛道汇总库.json
```

- `赛道与内容数据库.md` 是唯一汇总入口。
- 单赛道页与总入口使用同一版表达。
- 汇总入口对应的 `赛道汇总库.json` 用 `core_track_keywords` 保存已确认的核心赛道词。
- `赛道汇总库.json` 保存四个前台部分、后台选题加工库、来源关联和聚合缺口。
- 单条爆款的 01—10 拆解、逐字稿、评论、视觉证据和数据快照继续作为证据层。
- 迁移旧库时先保存迁移前快照，再停止旧入口继续更新。

## 01 赛道理解

用一至三段自然语言说明：

- 这个行业表面在讨论什么，底层反复解决哪些问题；
- 用户最容易对哪些具体处境、选择和结果产生兴趣；
- 常见产品与服务怎样围绕这些需求形成变现；
- 当前仍有哪些内容或服务缺口值得长期观察。

赛道理解来自问题池、用户语言、传播规律和跨样本答案的归纳。它属于赛道级判断，需要保留后台依据与适用范围；单条爆款不能直接生成整段行业结论。

只有完整全文、尚未完成当前标准拆解的历史赛道，可以先建立“初步问题地图”，后台必须标记证据层级和待拆解状态。缺评论时不归纳用户态度，缺平台数据时不沉淀传播规律。

前台写成可连续阅读的行业介绍，不写研究报告式字段，不罗列证据状态和样本数量。

## 02 赛道问题池

汇总正式拆解卡中的“赛道问题”，在后台保留原始问法、来源、频率、证据身份、适用条件和修订关系。

### 合并规则

- 同一对象在相近场景中追求同一结果，且差异不会改变答案时，合并成一个主问题。
- 对象、阶段、场景或决策后果会改变答案时分开保留。
- 合并后仍要挂回全部原始问题和来源。
- 正式库更新时必须执行跨样本语义合并，不能保持“一条样本对应一个问题”的机械状态。

### 前台表达

- 展示合并后的完整问题句，不只显示抽象分类词。
- 使用日常问话，减少模板化长句。
- 不显示问题编号、数量、证据状态、代表样本和归并过程。
- 问题池需要覆盖本赛道现有问题的完整语义范围。

## 后台：选题加工库

保存元素迁移、选题具体化、收益显化和损失显化等加工动作，并记录适用问题、来源、成立条件、边界和反例。

它记录历史样本实际使用过的加工动作，帮助用户研究一条选题怎样形成；不作为前台栏目，也不作为当次候选生成的直接输入。

## 03 用户语言与评论问题库

这一部分需要从“收集原话”继续推进到“理解用户怎样回应内容”。后台保存真实评论、访谈、咨询、搜索问句、真实问答和发布复盘中的逐条原话；前台按四类形成用户回应地图：

1. **用户容易认可什么**：哪些观点、情境、方法或结果会被用户接住；
2. **用户会继续追问什么**：哪些内容引出了适配、效果、方法和下一步问题；
3. **用户会质疑或反对什么**：哪些论断、承诺、表达或做法容易引起异议；
4. **这些反应说明什么**：综合认可、追问和反对，判断用户真正看重的价值与边界。

每条前台判断至少由一条真实评论支持；跨样本判断要保留多条来源。评论只能验证发布后用户接住了什么，不能单独证明点击、完播或传播原因。

剧情对白、作者自问自答、角色扮演和 AI 演绎不能冒充用户语言。评论不可得时保留后台缺口，不用作者正文补齐。前台可以显示少量代表原话，不显示语言 ID、证据状态、互动数和抓取说明。

## 04 赛道传播规律

只保存多个独立、可比样本反复出现的赛道级传播认识。单条拆解中的传播判断先留作后台候选；不同平台、时间窗口和数据口径不得静默混算。

前台用自然语言呈现规律，不显示样本数、证据强度、代表样本和数据限制。相关依据完整保存在后台。

## 选题共创怎样读取数据库

1. 锁定当前赛道和当前内容任务；
2. 只读取赛道问题池中的完整问题句及其来源索引；
3. 选择与当前任务相关的问题；
4. 按独立的选题加工规则先校准口味、锁定目标客户损益，再选择问题发展路径并按需使用底层加工动作；
5. 生成并校验本次候选清单。

赛道理解、用户语言、传播规律和后台选题加工记录不参与候选命题。候选清单保存在当前内容任务中；用户选择后再进入生产决策并补充本人材料、内容答案与框架。

## 单条拆解写回链

`单条拆解卡 → 提取问题/评论/传播信号/加工动作 → 跨样本归并 → 更新赛道理解与三个稳定信息池 → 当次选题共创`

- 赛道问题先进入后台问题池，再与已有问题做语义归并。
- 原作的选题加工进入后台加工候选。
- 评论原话、追问和反对进入用户语言库。
- 单条传播判断先作为候选，跨样本复核后才进入正式传播规律。
- 多条样本积累出新的行业判断时，修订赛道理解并保留依据。

## 通用编译

所有 IP、学员和多赛道项目统一执行 [赛道数据库通用编译合同](track-database-compilation-contract.md)。禁止继续使用写死项目绝对路径、赛道名称、核心词、问题句、用户判断或传播结论的临时生成程序。

内容编导先把单条拆解增量和跨样本归并结果写入 `赛道数据库编译资料包.json`；通用编译器核对问题覆盖、合并审计、评论证据、跨样本传播依据和赛道角色，再生成前台页面与结构化数据库。编译结果先进入空白暂存目录，通过独立验收后才切换正式入口。

## 新建、迁移与验收

迁移顺序：保留旧入口快照；建立唯一记录与十步详情；生成后台关联；迁移和归并问题；迁移用户语言；复核传播规律；形成赛道理解；把历史高价值选题与当前机会移出正式数据库；最后切换入口。

更新完成后调用：

```bash
node scripts/compile-track-database.mjs \
  --manifest <赛道数据库编译资料包.json> \
  --out <空白暂存目录>

node scripts/validate-track-database-v2.mjs <赛道汇总库.json> [赛道汇总页.md]
```

最低验收：

- 汇总入口页面标题为“赛道数据库”，不附加版本号或内部版本说明；
- 汇总入口标题下显示 1—3 个已确认的核心赛道词；工作接触赛道、任务词、相邻词和排除词不混入该行；
- 汇总入口对应的结构化数据库以 `core_track_keywords` 保存同一组词，前后台一致；
- 总入口按赛道分段，每个赛道按 01—04 顺序展示四部分；
- 前台与当前结构化数据库均不再包含高价值选题池和当前内容机会；
- 赛道理解覆盖行业焦点、用户兴趣、变现方式和长期缺口；
- 问题池完成语义合并，同时覆盖原问题的完整语义范围；
- 前台不显示问题 ID、样本数、证据状态、身份审计和运行说明；
- 后台每条记录仍能回链到十步详情、真实评论或其他直接证据；
- 正式样本数、详情页数和关联索引记录数一致；
- 历史详情页与采集参数保持不变。
- 编译资料包没有静默遗漏单条赛道问题；每条问题都有归并去向或排除理由。
- 业务接触赛道没有混入核心赛道词，也没有自动进入当前 IP 的选题来源。
- 用户回应判断只回链真实评论；正式传播规律至少连接两个独立样本。
